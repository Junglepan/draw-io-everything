# 图种与规范边界

| 核心问题 | 首选 | 边界 |
| --- | --- | --- |
| 步骤如何执行 | 基础流程图 | 标清条件和起止 |
| 谁负责哪一步 | 泳道流程图 | 泳道是职责组织方式 |
| 多参与方、事件和异常如何协作 | BPMN | 顺序流不跨池；跨参与方消息另用消息流 |
| 系统之间按什么顺序交互 | UML 时序图 | 同步、异步、回复消息分别表达；PlantUML 工作流见 [sequence-diagrams.md](sequence-diagrams.md)，draw.io 仍可按指定格式交付 |
| 对象如何改变状态 | UML 状态机图 | 状态不是操作步骤 |
| 系统与谁交互 | C4 上下文 | 不展开内部应用 |
| 系统由哪些运行单元构成 | C4 容器 | 容器不等于 Docker |
| 某应用内部如何分工 | C4/UML 组件图 | 固定一种表示法 |
| 实例部署在哪里 | 部署图 | 区分逻辑对象与实例 |
| 数据有哪些关系 | ER 图 | 基数与可选性来自实际约束，不统一为一对一 |
| 数据如何流动 | DFD/血缘图 | 数据流不等于控制顺序 |

横向、纵向、分层、环形是布局；业务、技术、数据架构是视角。一个问题涉及结构、交互和状态时，用配套视图而非一张巨图。

标准语义优先于源图风格。UML 异步消息使用实线开放箭头，回复消息使用虚线；不能从“异步=虚线”的个人架构图惯例迁移到 UML 时序图。BPMN 网关符号不能因风格统一被替换。ER 关系根据模型约束选择基数。C4 不强制蓝灰配色。

需要严格符合标准时记录版本并查相应官方规范；目前仅提供常见选型边界，不能声称覆盖标准全文。

- BPMN：https://www.omg.org/spec/BPMN/
- UML：https://www.omg.org/spec/UML/
- C4：https://c4model.com/diagrams
- ER 图工具指南：https://www.drawio.com/docs/diagram-types/entity-relationship-tables/

## 多视图组织复杂方案

当方案同时涉及过程、结构、控制与实施安排时，按读者问题选择配套视图，不要求每张图包含所有区域：

| 视图 | 回答的问题 | 可选组织方式 |
| --- | --- | --- |
| 端到端过程 | 工作如何推进、在哪里交接？ | 阶段卡片、主链流程、责任泳道 |
| 系统职责 | 谁负责什么、结果由谁维护？ | 分层行带、能力分区、系统分解 |
| 控制机制 | 什么条件允许推进、何时结束？ | 状态链、门槛、出口条件 |
| 实施安排 | 先做什么、完成后怎样验收？ | 优先级—事项—验收效果列表 |

跨视图的同一对象保持名称与含义一致。整体排版可以统一，内部结构服从各自问题；不为了外观一致强制使用相同骨架。选构图与局部表达时，按需参考 [构图与局部模式](composition-patterns.md)。
