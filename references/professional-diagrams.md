# 专业图：先决定要解释的关系

当用户需要接近真实业务的复杂图，或认为示例过于简单时，先确定读者需要作出的判断，再选择相应示例。复杂度来自必要的信息与关系，不以节点数量达标。

## 四种表达方式

| 问题 | 结构与视觉语言 | 必须交代的细节 |
| --- | --- | --- |
| 谁与哪些系统协作？ | 人员、系统、组织边界；节点名称/类型/职责分层；关系标签 | 所有权、抽象层级、交互目的；技术协议仅在有意义时补充 |
| 跨组织业务如何完成？ | 参与者池与职责泳道；任务、事件、网关各用其符号 | 消息与顺序区别，条件出口、失败终点和重新进入的位置 |
| 一个字段变更会影响什么？ | 来源→转换→数据模型→消费；字段行连接；主路径强调 | 粒度、去重、聚合、空值与退款口径；未展示字段不能误称不存在 |
| 批处理如何在失败时收敛？ | 主轴、循环边界、侧向异常、明确汇合点 | 重试上限、退避、游标推进、取消检查点与最终状态 |

## 信息与视觉的平衡

- 标题交代范围，副标题交代关键假设；图例解释本图确实使用的约定。
- 名称作为第一层，类型与职责作为第二层；数据表还可有字段与键标记。不要让辅助信息抢占主要关系。
- 颜色只承担明确含义，例如所有权或当前影响路径。线条和文本也能区分状态，不单靠色相。
- 对齐相同层级；给跨区关系预留通道。优先通过端口与途经点解决绕行，不用大幅缩小文字压缩画布。
- 源图中的 UI 控件、无含义图标和低对比度非焦点线条不必复制到静态工程图。
- 仿手绘外观可作为独立审美选择；任务、事件、判断、消息的专业语义仍需准确。
- 超出一张图可解释的范围时拆为总览与细节。总览不删除解释关键结论所必需的连接。

## 质量门槛

1. 建立虚构场景或实际需求的事实表：参与者、关系、输入输出、失败与终止条件。
2. 查明所用表示法。把“参考图看起来这样”与标准规定分开；不复制错误符号。
3. 验证 XML 与实际渲染。检查路由是否改变读者理解、标签是否归属正确。
4. 面向读者检查：能否顺着流程得到终点，或顺着血缘解释指标来源？
5. 记录具体验证范围。示例验证通过不意味着拥有通用排版引擎或标准认证。
